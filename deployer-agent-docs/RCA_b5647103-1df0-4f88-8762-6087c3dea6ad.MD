# RCA — WhatsApp connection fails in production (brazil-feijoada)

## Problem statement
User (pt-BR): "após ser publicado o sistema de conexão ao whatsapp não funciona" — after publishing, the WhatsApp connect flow (QR via `POST /api/whatsapp/start`, status via `GET /api/whatsapp/status`) does not work in production. Works in preview.

## Verified production state
- Deployment `brazil-feijoada`, active run `b5647103-1df0-4f88-8762-6087c3dea6ad`, template `farm_ts_react_mongo_base_image`, tier_0, k8s frontend. Run status: success (app itself is live).
- `GET /api/whatsapp/status` on the live URL returns **401** (`Sessão expirada`) — i.e. the backend is up and routing; this is just the auth wall, not the bug.
- Secrets: `WHATSAPP_SERVICE_URL` and `WHATSAPP_INTERNAL_TOKEN` are **both present / non-empty**. `WHATSAPP_SERVICE_URL` **matches `http://localhost:8002`** (confirmed via list_secrets equals-check). So secrets are NOT the problem — the value is the same localhost:8002 as preview.

## Root cause (proven)
The production pod never runs the Node.js Baileys bridge (`/app/whatsapp-service/index.js`). Nothing listens on `localhost:8002`, so `lib/ai.py:wa_call` cannot reach it and returns `{"status":"offline"}` — the connect/QR flow silently fails.

Evidence from the run's own source (eph sandbox):
1. **`entrypoint.sh`** (the production PID 1) starts only two processes: it parses `[program:backend]` out of supervisord.conf and runs `uvicorn server:app` (minus `--reload`), then starts `nginx`. There is **no code path that launches the whatsapp-service node process**.
2. **`etc/supervisor/conf.d/supervisord.conf`** is a READONLY file and defines only `backend`, `frontend`, `mongodb`. The preview-only supervisor program named `whatsapp` (node index.js, WHATSAPP_PORT=8002) is **not in this committed file** and is **not read by the production entrypoint** (entrypoint only consumes the `[program:backend]` section). `frontend` and `mongodb` are preview-only too.
3. **`Dockerfile`** installs/builds only the frontend (`yarn install && yarn build`). It does **not** install a Node runtime for the service, does **not** run `yarn install` inside `whatsapp-service/`, and does **not** copy/launch the bridge. The deployed base-image runtime is not guaranteed to even contain `node`.
4. `backend/.env` and `backend/lib/ai.py:45` default `WHATSAPP_SERVICE_URL` to `http://localhost:8002`; prod secret is the same value — correct target, but nothing is bound to that port in prod.

Net: the extra Baileys process that exists only because preview's supervisor started it is not reproduced by the production image. In prod there is exactly one app process (uvicorn) + nginx.

## Concrete fix needed (E1 / code)
The production image must both contain Node AND actually start the bridge. Two parts:

1. **Dockerfile** (repo root, `Dockerfile` + `Dockerfile.cloudbuild`): add a Node runtime and install the service deps, e.g. copy `whatsapp-service/` and run `yarn install` there (using the committed `yarn.lock`).
2. **Start the bridge in prod.** Either:
   - (a) Edit `entrypoint.sh` to launch the bridge as a second long-running process alongside uvicorn: `WHATSAPP_PORT=8002 node /app/whatsapp-service/index.js &` (with its env: `WHATSAPP_INTERNAL_TOKEN`, `WHATSAPP_AUTH_DIR`, `BACKEND_URL=http://localhost:8001`), and include it in the process-death/trap handling; or
   - (b) Have the FastAPI backend spawn/supervise the node process on startup. Still requires Node present in the image (part 1).

`WHATSAPP_SERVICE_URL=http://localhost:8002` can stay as-is once the bridge runs in the same pod.

### Also flag to E1 (will bite even after the bridge runs)
- **Baileys auth is ephemeral.** `WHATSAPP_AUTH_DIR=/app/whatsapp-service/auth` lives in the container filesystem and is wiped on every pod restart/redeploy → the user must re-scan the QR each time. Persist auth state (e.g. store Baileys creds in Mongo, or a persistent volume).
- **tier_0 memory.** Adding a second (Node/Baileys) process raises memory footprint; watch for OOMKills after the change and bump the tier if needed.

## Not the cause (ruled out)
- Secrets: present and correct (`WHATSAPP_SERVICE_URL` = localhost:8002, token set).
- Backend/app down: no — status route returns 401, app is live.
- This is an architectural gap in how the multi-process app maps onto the single-process FARM image, not a secret or data issue.
